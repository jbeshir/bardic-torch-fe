# Testing

Tests come in three layers:

| layer    | what it covers                                                                 | where                                                                      | command                            |
| -------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------- | ---------------------------------- |
| unit     | components, hooks, helpers, server modules, loaders and actions                | next to the code, `app/**/*.test.{ts,tsx}`; scripts in `scripts/*.test.ts` | `npm run test:run` (in `validate`) |
| contract | the vendored spec, the generated types and the fixture API                     | `test/contract/`                                                           | `npm run test:run` (in `validate`) |
| e2e      | the built Worker in Chromium, served by `wrangler dev` against the fixture API | `e2e/`                                                                     | `npm run test:e2e`                 |

`npm run validate` also runs these repository scans, all as vitest tests in `test/`:

- `repo-hygiene.test.ts`:
  - exact pins and no feed leftovers;
  - the one dependency override (`typescript`), one locked version of `@playwright/test`, `playwright` and `playwright-core`, and an `allowScripts` decision for every locked package with an install script (read from `package-lock.json`, so a version bump fails until it is decided again, and none is stale);
  - no e2e code makes its own Playwright `APIRequestContext`, and no link component takes a `target`;
  - the original wiki's host only in the allowed files;
  - `.prettierignore` holds exactly the expected entries;
  - the CI workflows (`validate` and `e2e` in `ci.yml`, `audit` in `audit.yml` on every push and pull request; every action pinned to a 40-hex commit SHA with its `# vX.Y.Z` tag, one pin per action; only a superseded pull request run is cancelled; checkouts keep no token; the audit and audit:signatures scripts), the ops files (`wrangler.jsonc`, parsed with TypeScript's JSONC parser: both Workers, their custom domains (no `www`: it is a redirect rule), variables, required secrets, compatibility date and flags; `.dev.vars.example`; the generated `Env` in `worker-configuration.d.ts`, which `check:types` keeps fresh; `public/_headers`; and no `public/_routes.json`) and these docs.
- `config-imports.test.ts`: the config files Vite loads natively (`vite.config.ts`, `vitest.config.ts` and what they import) use explicit `.ts` import specifiers and relative paths (no `~/` alias), and only erasable TypeScript (no enums or parameter properties). Breaking this brings back the "config loaded by the bundler" build warning.
- `no-raw-colours.test.ts`: colour only from the tokens.
- `motion.test.ts`: movement only under `motion-safe:`.
- `lint-coverage.test.ts`: ESLint (`eslint.config.ts`) lints every code file (`.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`: scripts and config files too) with the import rules at error, and every code file is in knip's project (`knip.json`), which checks unused files, exports and dependencies (`npm run check:unused`).
- `readonly-props.test.ts`: every component's props (and every hook's options object) are `readonly`.
- `component-usage.test.ts`, a second check after knip's: every export of an app module (components, server, schemas, constants, hooks, contexts, content; not the framework-read routes, root and entries, nor `app/test`) is imported by non-test code, not only by tests.

The scans walk the tree with one helper, `filesUnder` (`test/support/files.ts`), which skips the gitignored e2e screenshots.

It also runs the checks `check:types`, `check:api`, `check:tokens`, `check:contrast` and `check:prod-build`. See CLAUDE.md for what each does.

## Deviation from the product plan (PLAN §9)

The product plan has `npm run validate` cover the Playwright suite too. In FE1 it doesn't. **`npm run test:e2e` is a separate command**, because it needs Chromium and two full builds. Validate stays runnable anywhere Node runs, including sandboxes without browsers.

CI runs both, and both jobs are required on `main` (with `audit`), so nothing merges without e2e. CLAUDE.md has the two-image recipe for sandboxes.

Other FE1 differences from the plan's test list follow from the real API (no revoked or expired tokens to show) and are recorded in the chunk summaries.

## Unit tests

- **Environment by file name only.** `vitest.config.ts` has two projects: `dom` runs `*.test.tsx` in jsdom, `node` runs every other test in node, like the Workers runtime. A test that needs a DOM is a `.test.tsx` file (e.g. `test/cut-off.test.tsx`), never a per-file pragma; `test/environments.test.ts` proves the split. vitest has its own config, so it never loads the React Router or Cloudflare plugins (no dev server, no workerd). It aliases `virtual:react-router/server-build` to `test/support/server-build-stub.ts` (the tests that import the Worker entry `vi.mock` it), and `react-dom/server` to `react-dom/server.edge`, the build Workers resolve, which has `renderToReadableStream`.
- **The Node versions.** The suite runs on `.nvmrc`'s Node 26.13.0, and the migration gates also ran it on Node 22.23.3 and 24.17.0. Node ≥ 24's fetch (undici ≥ 7) rejects an `AbortSignal` that isn't its own, which broke every router navigation and submission in jsdom until vitest 4 gave jsdom Node's `AbortController`. `app/test/abort-signal.test.tsx` fails if that regresses: a `Request` takes the environment's signal, and a `<Form method="post">` submission reaches its action. `renderRoutes` returns only once the router has run its initial loaders and React has committed the page: `act` waits for microtasks, and a loader that fetches through msw takes several macrotasks, so on Node 24 a test that clicked straight away found the empty `HydrateFallback`, ended, and left the fetch to hit the closed msw server (`ENOTFOUND api.test`).
- **Accessible names in jsdom.** Testing Library's name algorithm trims every child element's text, and only separates children that aren't `display: inline`. jsdom 30 computes HTML's default `display`, so `Moods<span> (optional)</span>` would be named "Moods(optional)", which no browser does. `app/test/setup.ts` gives inline phrasing elements a non-inline display, which is how jsdom up to 29 behaved (it computed none), so names keep the browser's word breaks.
- **Components** use testing-library and `@testing-library/user-event`.
  - Test every state, and the keyboard.
  - `expectSameMarkupInBothThemes` in `app/test/themes.ts` is a **guard, not theme coverage**: it fails only if a component starts branching on the theme. It says nothing about how either theme looks. The theme evidence is `check:contrast` (every token pair in both themes) and the e2e checkpoints (axe and screenshots in both themes, each asserting that the page paints that theme).
  - `renderWithRouter` and `renderRoutes` (`app/test/router.tsx`) supply React Router's framework context (`UNSAFE_FrameworkContext`).
- **Loaders and actions** run against the fixture API through msw:

  ```ts
  import { serveFixtureApi } from "~/test/msw";
  import { loadContext, sessionCookie, sessionTokens } from "~/test/context";

  const api = serveFixtureApi(); // fresh fixture state per test

  const cookie = await sessionCookie(
    sessionTokens({ accessToken: "fixture:contributor" })
  );
  ```
  - **Every msw server comes from `serveMocks()`** (`app/test/msw.ts`; `serveFixtureApi()` uses it). msw 3 imports `http`/`HttpResponse` from `msw/http` and `delay` from `msw/utils/delay`. A request no handler answers (msw's `onUnhandledFrame`) is refused **and fails the test** that made it, so a test can't pass because the code under test turned msw's refusal into a 502. `server.use()` adds one test's handlers, e.g. a fake Auth0 token endpoint answering with Auth0's real response shapes.
  - `loadContext()` gives a validated env whose API base URL is `https://api.test`.
  - `formRequest()` builds a same-origin, form-encoded request.
  - `runAction()` (`app/test/proxy.ts`) runs a proxy action.
  - `serveApp()` (`app/test/server-build.ts`) renders routes through the real `entry.server` for header and nonce tests. A client navigation's data is a single fetch `.data` request (`/_root.data` for `/`, `?_routes=` naming the loaders to run). `app/test/single-fetch.ts` decodes its turbo-stream body the way React Router's client does.

- **Catalogue pages (FE2)** copy `/pieces`, the first of them:
  - **helpers** each have a table test: `app/catalogue/query-state.test.ts` lists every canonicalisation rule as `[why, query, canonical, 200 | 301]` (at least 60 rows) and checks, for every row, that the canonical form is answered 200 (no redirect loop), parses back to the same state and is what `href` gives; `paging.test.ts` has the paging edges (empty list, exactly full page, page 201/202);
  - **the read client** (`app/server/catalogue.server.test.ts`) checks what it sends (only `Accept`; the query serialised in the spec's order) and maps every upstream answer to its `ReadFailure`;
  - **each route's loader and documents** are `<route>.ssr.test.ts`: the loader on its own (`routeArgs`, a thrown redirect or `data()` caught and returned) for the canonical and paging redirects and every status the spec declares for each operation it calls (a real invalid parameter for the 400, `fail` for the 500), a network failure (`HttpResponse.error()`), a malformed body (`offContractResponse`), a proxy's plain-text 503 (`POST /__fixtures/outage` through msw) and a timeout (`AbortSignal.timeout` spied down to 20 ms with an msw `delay("infinite")`); then the documents through `serveApp`: titles, canonical and robots, the failure pages, and `Retry-After` with the right `Cache-Control` signed out (`private, no-cache`) and signed in (`no-store`), for a document and for a `.data` request with the root in `_routes` (as Try again sends it; a plain navigation leaves the root out, so its `.data` answer is `private, no-cache` on every page);
  - **each route's component** is `<route>.test.tsx`: `renderRoutes` with a stubbed loader (and a `HydrateFallback`) for every state, the error boundary, the keyboard, and `aria-busy` on the results while a deferred loader is pending.

- **Sentry (R28):** `app/contexts/SentryContext.test.tsx` mocks `@sentry/react`: no init without a DSN, one init with it across navigations, and an error page that is the first render starts Sentry before reporting. Two of its tests use the real browser SDK with a recording transport: nothing about the reader is sent (no cookies, headers, body, query string or IP address), and navigations are traced by URL path, without the query string. `app/entry.server.test.ts` mocks `@sentry/cloudflare`: loader and render errors are reported (abandoned requests are not). `app/server/worker.server.test.ts` checks the server's envelopes, with the real `@sentry/cloudflare` `withSentry` and a recording transport: a loader's error is reported once, without the request's query string, cookies, headers or IP address, and spans go without its query string, headers or body. `sentry.server.test.ts` checks the server gets no DSN when `SENTRY_DSN` is unset or empty. Delivery to a real Sentry is not part of any test run.
- **Cookie bytes:** `app/server/cookie-format.golden.test.ts` pins the exact `Set-Cookie` strings of `__Host-bt_session` and `__Host-bt_return_to` for a fixed secret and payload, and parses them back. Its expected strings are golden: a library change that alters them would sign every reader out, so fix the code, never the strings.
- **Markdown help pages:** `compileMarkdown` and `FRONTMATTER` (`app/test/markdown.ts`) compile with the real pipeline.

## The fixture API

`test/fixture-api/` is a fake of the backend. It serves the FE1 operations (`getMe`, `updateMe`, `listAPITokens`, `createAPIToken`, `revokeAPIToken`), `getHealthz` for readiness, and the 17 public catalogue reads (`listPieces`, `getPiece` and the rest, in `catalogue-operations.ts`, merged into the table), all against the catalogue data below.

- **One operation table, three transports.** `operations.ts` is keyed by `operationId`, and `router.ts` routes requests to it. The same router serves:
  - msw in unit tests (`app/test/msw.ts`);
  - the Node server in e2e and `dev:fixtures` (`server.ts`, `npx tsx test/fixture-api/server.ts`, on `127.0.0.1:$PORT`, default 4010);
  - the contract scenarios.
- **It mirrors the backend's rules:**
  - display names are NFC-normalised and trimmed, 1–64 characters, with no control or format characters;
  - token names are at most 128 characters;
  - a user may have at most 10 active tokens (409 `token_limit_reached`);
  - the token list is active only, newest first;
  - non-JSON bodies get 415 and bodies over 16 KiB get 413.
- **Catalogue requests are parsed strictly** (`catalogue/query.ts`), as the backend does (`api/openapi.yaml`, and the API docs' "Notes for FE2"). The rules come from each operation's parameter list in the spec; a parameter schema the parser doesn't understand throws when it loads. Each of these is 400 `invalid_request`:
  - a path slug that doesn't match `^[a-z0-9]+(-[a-z0-9]+)*$` or is over 191 characters; an id that isn't a canonical positive int64 (no leading zero or sign, at most 9223372036854775807);
  - a query string that isn't validly percent-encoded, or isn't UTF-8 (even in a parameter the operation ignores);
  - a scalar parameter given more than once. Only `term`, `kind` and `conservation_status` (pieces), `kind` and `role` (persons) and collection `kind` repeat, as `?kind=song&kind=poem` (form, explode); a comma list is one unknown value;
  - a value outside its enum (`letter` is `A`–`Z` or `0`), a repeated value of a `uniqueItems` parameter, or more values than `maxItems` (more than 20 distinct `term`s; a repeated `term` counts once);
  - a `stub` other than `true` or `false`; a `limit` outside 1–100 or an `offset` outside 0–10000, or either not in canonical decimal (`05`, `+5`, `1e3` and empty are 400);
  - a `q` that is empty, only ASCII blanks (space, tab, line feed, form feed, carriage return; a no-break space is a character) or over 200 code points;
  - `sort=relevance` without `q`;
  - a `term` no public piece term has ("unknown term: <slug>": unknown, unapproved, under an unapproved parent, or an affiliation term), or an `affiliation` no public affiliation term has ("unknown affiliation: <slug>"). The lookup is `publicTermFacet` in `catalogue/visibility.ts`.

  Unknown query parameters are ignored, repeated or not. A path parameter that decodes to contain `/` (a raw `%2F`), or isn't validly percent-encoded, matches no route: 404 `not_found` "no such route", for every operation. Handlers get the decoded declared parameters only (`query`, a `URLSearchParams`). `test/contract/requests.ts` lists a request for every rule; they run through the router and over HTTP.

- **It is checked against the contract.** Every response is validated against `api/openapi.yaml` (ajv, draft 2020-12) before it is returned. A fixture that breaks the contract throws, and the server answers 500. OpenAPI's `discriminator` (on `Revision`) is declared to ajv as an annotation: the `oneOf` under it does the validating, as each branch is closed with a one-value `entity_type`.
- **State is per user.** Only `Authorization: Bearer auth0|fixture:<userId>` authenticates; a stub session's access token is `fixture:<userId>`. Anything else gets 401 `unauthenticated`. The seed users are `contributor` ("Morwen of the Marches") and `moderator` ("Master Tobias Fiddler"). They are invented stage names, as every fixture name must be.
- **Control endpoints** (Node server and msw):
  - `POST /__fixtures/users {role?, display_name?, tokens?: "sample" | "none", blocked?}` → 201 `{id}`. This creates an isolated user. A blocked user gets 403 `user_blocked` from every operation.
  - `POST /__fixtures/fail {operationId, status, code?, times?, userId?, match?}` → 204. The next `times` (default 1) calls fail with that status and code. Only pairs the spec allows for the operation are accepted. An authenticated operation fails for `userId` only. A public catalogue read is parsed first, so an invalid request still gets its 400 and leaves the failure queued.
  - `POST /__fixtures/outage {operationId, match?, times?, mode: "503" | "html-502"}` → 204, for public operations only. The next matching `times` calls get what a proxy in front of the backend sends when it is down: a plain-text 503 (dokku) or an HTML 502 (Cloudflare). It answers before the backend would, so even an invalid request gets it. It is deliberately outside the spec: the only response the router doesn't validate.
  - **`match`** is an object of path or query parameters of the operation, with string values: `{slug: "e2e-500-a1"}`, `{q: "timeout-7f2"}`. A failure or outage fires only for a request whose parameters include every pair (a repeated parameter matches if any of its values does). Failures and outages with different matches are kept apart.
  - **On the Node server, a public operation's failure or outage needs a non-empty `match`**, because every e2e worker shares the server: an unmatched one would fail another test's request. Use a value unique to the test. In msw (fresh state per test) `match` is optional; without it every call fails.

  In e2e use `createFixtureUser(request, options)`, `failNext(request, {...})` (with `userId` or `match`) and `outageNext(request, {operationId, match, mode, times?})` from `e2e/support/fixture-api.ts`; `e2e/prod/fixture-api.spec.ts` checks them against the shared server. In unit tests, `serveFixtureApi().fail({...})` queues a failure directly (`addFailure` in `router.ts`), without the endpoint's status and code check, for a pair the operation doesn't list (such as `unavailable` at 500); the response is still validated against the spec.

- **Idle keep-alive sockets stay open.** The server sets `keepAliveTimeout = 0`, so only the client ever ends a keep-alive connection. With Node's default (5 s, plus a 1 s buffer) a client whose event loop runs late, such as a Playwright worker busy with axe and full-page screenshots, or workerd, can send on a socket the server has just closed, and gets `ECONNRESET` ("socket hang up"); a repro with a starved client failed 4/4 with the default and 0/4 with 0. `test/contract/server.test.ts` checks the setting, and that a second request on one socket after 6.5 s idle is answered (about 7 s). Retries would only hide it. The other hop, Playwright to `wrangler dev` on 8788, is covered too: wrangler dev 4.156.1 sends no `Keep-Alive` hint and doesn't close an idle socket within a test's lifetime (measured), and `e2e/prod/keepalive.spec.ts` pins it (a raw socket, `GET /favicon.svg`, 6.5 s idle, then a second request on the same socket answered 200). `test/repo-hygiene.test.ts` checks that every e2e API request uses the per-test `request` fixture or `page.request`, never an API context of its own. Which hop the original "socket hang up" came from is unknown: no trace of it exists, and the FE1 baseline run had none.
- **Contract tests.** `test/contract/scenarios.ts` lists, for each of the 17 public catalogue reads, a success and one case for every status the spec declares (400 from a real invalid parameter, 404 from an unknown slug or id, 500 injected with `fail` and a `match`, as the Node server requires), plus a `%2F` in each path parameter → 404 "no such route"; the FE1 operations have at least one success and one error each. `fixtures.test.ts` checks the matrix against the spec's declared statuses, so a new status without a scenario fails. They run through the router (`fixtures.test.ts`), over HTTP (`server.test.ts`) and through msw (`app/test/msw.test.ts`). `spec.test.ts` checks that the spec is valid OpenAPI 3.1 and has the FE1 operations; `generated-types.test.ts` pins the generated types FE1 relies on.

### Catalogue data

`test/fixture-api/catalogue/` holds the raw records the catalogue reads are served from: `terms.ts`, `persons.ts`, `pieces.ts`, `links.ts` (a link has one owner, may carry performances, and may be hidden), `collections.ts`, `events.ts`, `revisions.ts` and `generated.ts`. Each record is typed against `components["schemas"]` (with slugs in place of nested objects, and local fields for what the API never serves). `catalogue-data.test.ts` imports every module and checks the rows of the plan's data table and every reference between the tables.

- **Everything is invented.** Every person, user, contributor and uploader is an invented stage name; titles and notes are short invented prose, and there are no lyrics. The real wiki supplied only the vocabulary (facets, kinds, tree shapes). The repository can't carry a denylist of real names, so the check is a one-off script run outside it (`/workspace/privacy-check/`, see the C1.4 report) and again by the reviewer; add a name to the fixtures only after thinking of it yourself.
- **Raw means unredacted, on purpose.** The records include what is never served: an unapproved term (`draft-topic`) and its child, a hidden link on the Copper Kettle, a hidden legal alias on Wren, a credit by a person who now has no page, and a pending revision (1015, `UNAPPROVED_REVISIONS`). Their marker text starts `HIDDEN-`, so the leak scan (below) can look for it in any response.
- **Facts the e2e relies on.** `the-dragons-hoard` is restricted; its links are on `private-recordings.example`; it is credited to Wren, performed at Muster Field and Midwinter Revel, cited in The Northmarch Songbook, and its user revision 1005 has a base from before the restriction. Revision 1003 is the piece diff.
- **The generator is deterministic.** `generated.ts` makes 205 practice pieces ("Drill Song 001" to "205"), their links, and 202 performances at Muster Field (203 with the Dragon's Hoard one); it uses no clock and no randomness, and the test calls it twice.
- **Short pages stay short.** The test pins the pages the screenshots rely on (the letter T, poems with the eerie mood, the swords category, the songbook's citations, Midwinter Revel); about 249 pieces give five pages of 50.

### Catalogue semantics

The operations mirror the backend's (`api/openapi.yaml`, the API docs' "Notes for FE2", BE PLAN §4.1). `catalogue/visibility.ts` holds the redaction and builds every served body; `catalogue/search.ts` the searchable lists and counts; `catalogue/text.ts` the text rules both use. `catalogue/catalogue.test.ts` checks them through the router (so every body is also validated against the spec), against expectations worked out by hand from the data.

- **Visibility.** A term that is unapproved, or under an unapproved one, is never listed, matched, counted or referred to (404 on its own reads). A person who prefers no page is listed as a stub (`is_stub: true`) with `profile: null`, and is dropped from credits (the whole credit row), performer lists, relations, term member lists and `person_count`s, citations and needs-work; `q` matches them by name only, and no `role` or `affiliation` filter matches them. Hidden aliases never appear or match; hidden links never appear, nor do the performances they record.
- **Faceted piece search.** `term`s are grouped by facet: OR within a facet, AND across, each matching the term or any public descendant (a piece tagged with a term and its child counts once). `kind` (primary or secondary) and `conservation_status` are two more facets; `q`, `letter` and `stub` are plain filters. Counts are disjunctive: each value's count applies every filter but its own facet's (`letter` included, so `letters` ignore the letter filter). Only counts above zero are listed: `terms` by slug, `kinds` and `conservation_statuses` in enum order, `letters` with `0` first.
- **Sort keys and letters.** Titles and names of pieces, collections and persons skip leading punctuation and one leading "The", "A" or "An" (so "The Greywater Minstrels" sorts and counts under G); only events sort by name as written, and have no A–Z (api-docs, A–Z). Keys are compared with `Intl.Collator("en")` after folding case, accents and the letters NFKD leaves whole (ł, ø, đ/ð, æ, œ, ß, þ), punctuation dropped. A letter is the key's first character after NFKD and mark stripping, with Ł→L, Ø→O, Đ/Ð→D, Æ→A, Œ→O, ß→S, Þ→T; anything else is `0`. Ties are broken by the record's position in the data (the internal id), so pages are stable.
- **Search.** `q` is split on anything but letters, digits and underscores (marks removed, accents folded). A word counts if it has a letter or digit, is 3 to 84 characters (InnoDB's `innodb_ft_min_token_size` and `innodb_ft_max_token_size`) and isn't one of InnoDB's default stopwords ("and" is not one); at most 8 count. Each must start a word of the title, an alias or the notes (persons: the name or a public alias). With no word left ("the", "Oi"), the folded `q` must start the title or name. `relevance` (the default with `q`) ranks title matches, then alias, then notes, then by sort key; prefix matches all rank alike, so they come in sort-key order.
- **Other lists.** Terms come in tree order (facets in enum order, parents before children, siblings by position then display name), with distinct counts over public descendants. A term's members are pieces by sort title, or for an affiliation, persons with a page by name. Collections are by sort name, with `letters`; events by name. Person works (by piece title), person and event performances (newest year first, unknown last) and collection citations (by the owner's sort key) are capped at 200, with `*_total`. Needs-work lists pieces then persons, each by sort key; a restricted piece only for being a stub; `counts` has all four reasons whatever the filter.
- **Revisions.** History lists approved revisions only, newest first (`created_at`, then id); a pending revision is 404 by id. Snapshots are redacted by what is visible now: references are resolved to the entity as it is now, or dropped if it isn't public; a link is shown only if its URL is that of a visible link now; credits, performers and relations of persons without a page are dropped; a person's alias only if it is a public alias now, and their name only if it is their name or a public alias now (otherwise the current name). The base is shown only if it is an approved revision of the same entity, otherwise `base_revision_id` and `base_snapshot` are both null. `changed_fields` is computed on the redacted views (so a revision whose only changes are now redacted, like 1014, lists none), or with no base lists every non-empty field.
- **Unknown entities.** An unknown or non-public slug or id is 404 `not_found` "<entity> not found"; a raw `%2F` is 404 "no such route" (see above).
- **The leak scan.** The test sends every read of every entity (pieces, persons, all terms including the unapproved ones, collections, events, every revision id including the pending one, every history) and the lists with several filters, and asserts that no body contains a `HIDDEN-` marker or the unapproved term, and that a no-page person's slug appears only in person lists and on their own page. Each redaction rule was broken once by hand to see the test fail.
- **Known simplifications.** Relevance is a rank by field, not InnoDB's scores: the backend's order among matches can differ (its scores depend on index-wide statistics, drafts included), though which pieces match is the same. The backend has one FULLTEXT index over piece title and notes and one over aliases; the fixture lets the words of a query match across the title, aliases and notes together. Normalised-URL matching of snapshot links is exact URL equality. Every piece, person, collection and event in the data is approved, so only terms and revisions exercise the "unapproved" rules.

## Stub sign-in: three locks

e2e and `npm run dev:fixtures` sign in as fixture users without Auth0. `/auth/login?as=<userId>[&returnTo=/path]` sets a real `__Host-bt_session` whose access token is `fixture:<userId>`. Without `?as`, it shows a fixture-user chooser.

All three locks must open:

1. **Compile flag.** `__STUB_AUTH__` is true only in `e2e` and `development` builds. `app/server/stub-auth.server.ts` is reached only through `if (__STUB_AUTH__) await import(...)` inside the `/auth/login` loader. `check:prod-build` builds production and preview, and fails if either contains the stub module, its marker, or a fixture host.
2. **`AUTH_MODE=stub`** in the environment.
3. **A local host.** The request's host must be `localhost` or `127.0.0.1`.

If `AUTH_MODE=stub` reaches a build without the flag, it is ignored with a logged error, and `/auth/login` goes to Auth0. The prod e2e phase binds `AUTH_MODE=stub` on purpose to prove this ("AUTH_MODE=stub is ignored: /auth/login goes to Auth0").

## e2e

`npm run test:e2e` (`scripts/e2e.mjs`) runs two **phases**, one after the other, because both builds write `build/`:

- **prod**: `npm run build`, the real production build. Specs are in `e2e/prod/`: landing, help, theme, security headers and CSP, errors, signed-out settings, the catalogue's pages (`browse`, `search`, `piece`, `bard`, `directories`, `categories`, `collections`, `events`, `history`), `catalogue-journey` (the one cross-entity walk), `seo` (robots.txt, sitemaps and a piece's raw head, indexable) and `no-js`, stub ignored.
- **stub**: `npm run build:e2e`. Specs are in `e2e/stub/`: sign-in, account and settings, navigation, errors, the styleguide, forced colours, and `seo` (the not-indexable side: `Disallow: /` and `X-Robots-Tag: noindex`).

Both phases always run. The command fails if either one does.

**How each phase is served.** Playwright starts the fixture API on port 4010, then builds the phase and serves the build with `npx wrangler dev --port 8788 --ip 127.0.0.1 --live-reload=false --show-interactive-dev-session=false --infer-origin-from-routes=false --var NAME:VALUE …`. `wrangler dev` reads `.wrangler/deploy/config.json`, which points at the build's `build/server/wrangler.json`, so the compatibility date and flags come from the build. `--infer-origin-from-routes=false` keeps the real local origin, `localhost:8788`, instead of the production host wrangler would infer from `routes`: the stub sign-in host lock and the same-origin checks need it. The build's emitted `.dev.vars` is deleted (`scripts/build.mjs`), so only the `--var` bindings apply, among them `AUTH0_DOMAIN=auth0.invalid` and `AUTH_MODE=stub`. No phase sets `SENTRY_DSN`. The server runs with `CLOUDFLARE_CF_FETCH_ENABLED=false`: otherwise wrangler's local runtime fetches a sample `Request.cf` object from workers.cloudflare.com at start-up, which offline fails, warns and falls back to the same placeholder this uses at once (it was measured to happen at start-up only, never per request). Nothing depends on it. wrangler also warns that the required secrets are missing: they arrive as `--var` bindings, which it doesn't count as secrets, and the Worker sees them. Specs use `http://localhost:8788`, because Playwright's request context only sends Secure cookies over plain HTTP to `localhost`.

**Projects.** Each phase has two:

- `<phase>`: every spec except `no-js.spec.ts`;
- `<phase>-no-js`: `no-js.spec.ts` with JavaScript off for the whole context.

Both are followed by the `screenshots` teardown project.

**Network isolation.** Every spec imports `test` from `e2e/support/test.ts`. Its automatic network guard aborts, and fails the test on, any request to a host other than this machine. Chromium also gets a host-resolver rule that resolves nothing else. A test that expects a redirect off the machine (logout to Auth0) names the host in `offHostRedirects` and asserts that hop itself. The suite never needs network access or secrets.

**Workers, retries and timeouts.** There are 4 workers (see CLAUDE.md for why), a 90 s test timeout (a test that takes a checkpoint marks itself slow, which triples it to 270 s) and a 15 s `expect` timeout. Each test gets **one retry**, for the dev runtime's own flakes: `wrangler dev`'s proxy answers a POST or PATCH that was in flight when its workerd restarted with a 503 ("Your worker restarted mid-request"; it retries GETs itself). A test that passes only on its retry is _flaky_. `scripts/e2e.mjs` reads each phase's JSON report (`playwright-report/<phase>.json`) and prints every flaky test by name in a banner after the phase and again at the end, so a retry is never silent. Treat a flaky test as a bug to look into: the two the migration's gates saw were test races, fixed at their cause, not runtime flakes. A checkpoint's wait for transitions to finish also waited on elements Chromium doesn't render (the content of a closed `<details>`), where a transition was seen never to finish: no frame was painted while it waited, until the test timed out. It now waits only on rendered elements, and fails after 10 s naming whatever is still running. The toast checkpoint's success toast could auto-dismiss on a loaded runner before its focus held it, so its page clock is held until then. No gate run on wrangler 4 (stages 2b to 4, 3 full runs) showed the restart 503 or a "socket hang up" (both hops are covered, see [the fixture API](#the-fixture-api)), so the retry is kept as a guard, not used. Measured on 2026-11-02, after the race fixes: three full runs of the FE1 suite (both phases, 4 workers, the browser image) each passed 168 of 168 with no flaky test, no restart 503 and no socket hang up. The FE2 suite (the read UI added) is 287 tests: 181 in the prod phase (15.3 min) and 106 in the stub phase (18.0 min), about 33 minutes in all against a 40 minute budget, on the full gate run before the review fixes, with no flaky test. The server runs with `--live-reload=false`, and nothing writes the build it serves during a run. Don't build into `build/` while a run is going. Call `waitForHydration(page)` (`e2e/support/hydration.ts`) before any step that needs JS behaviour.

### Fonts

The sans is `system-ui`, whatever the machine has, so layout must not depend on its metrics. Two checks once did, and failed only on the bare `ubuntu-24.04` runner, where `system-ui` is DejaVu Sans (wider than the image's WenQuanYi Zen Hei):

- **The app bar covered the end of the page.** The bar was 56 px plus its 1 px top border, and the page kept 56 px for it. The check allowed 1 px, which hid that. It only failed when the page's height ended in a fraction rounded down (DejaVu: 3192.34375 px, a scroll extent of 3192). Now `h-app-bar` (the bar's whole box) and `pb-app-bar` are one expression. The check allows only the measured remainder the scroll extent's rounding leaves out of reach, which is under half a pixel.
- **The sidebar's Help group fell below the fold at 1280 × 800.** In FE1 the sidebar had a Browse note, whose line count depended on the font: with DejaVu it wrapped to one more line, and the last Help item ended 0.6 px past the fold. Even in the image it sat under the "more below" fade. Rows at lg are 28 px now (DESIGN §5.3), and the check asserts the Help group ends above the fade. FE2's catalogue navigation (Browse, Facets, Help: 18 single-line rows) has no such block: only a label that wraps adds a line (14 px) to its row.

`e2e/stub/navigation.spec.ts` runs both checks again with wider text (`applyWiderText`, 0.1em more letter spacing). Each variant asserts that the widening took effect: the page gets longer, and the sidebar's longest label ("Bard preference checklist") gets a longer text advance. Both checks pass with the image's fonts and with DejaVu Sans, plain and widened. The old layout (7675bb2) failed all four in both. The bar holds for any font by construction: the check also asserts that the bar is exactly as tall as the room under the page. The sidebar's fold is a budget, so text can always be too wide for it, but FE2's has room: at 1280 × 800 the last Help item ends at 692 px against the fade's top at 776 px, in both sans; DejaVu with 0.1em (and up to 0.2em) wraps one label and it ends at 706 px. It takes seven wrapped labels to pass the fade's top. Boxes that should line up are compared to within `SUB_PIXEL` (`e2e/support/layout.ts`, half a pixel), never 1 px. FE2's geometry follows the same rules: every page in the sweep gets the bar check plain and widened (above), the `/pieces` facet column at 1280 is checked left of the results and level with their top (within `SUB_PIXEL`) plain and widened (`prod/browse.spec.ts`), and the help infobox's width at 1280 is bounded by `w-infobox-xl` plus `SUB_PIXEL`, not plus 1 px.

To reproduce the bare runner's fonts in the image, point fontconfig at DejaVu (the `dejavu-fonts-ttf` package from the npm registry has the files), with a `fonts.conf` that includes `/etc/fonts/fonts.conf`, adds that directory and prefers DejaVu Sans for `sans-serif` and `system-ui`. Then run with `FONTCONFIG_FILE` set to that file.

### Checkpoints and screenshots

`checkpoint(page, name, options?)` (`e2e/support/journey.ts`) is the visual and accessibility gate for a page or state:

- **axe** with tags wcag2a, wcag2aa, wcag21a, wcag21aa and wcag22aa, in light and dark, at 360 and 1280 px. There must be zero violations.
- **Six PNGs** in `e2e/screenshots/`, named `{journey}-{checkpoint}-{light|dark}-{360x800|768x1024|1280x800}.png`. They are full-page unless `viewportOnly`. A state only one theme can reach is captured in that theme only: `checkpointThemes` in `checkpoints.ts` lists them (today just `theme/dark-choice`, dark).
- Before each capture it asserts that the page paints that theme's `canvas` token, so both-theme evidence is real. It also moves the pointer to the corner, so no hover is left over (hover is not captured; DESIGN §10.6).
- Full-page captures are taken scrolled to the top, so the sticky header is drawn at the top, not over the field a test scrolled to.
- Fraunces is `font-display: optional`, so a cold page load can keep the fallback serif. Before capturing, the checkpoint adds the same Fraunces files again from JS with `display: block` and waits for `document.fonts.ready`, so every capture shows the design face.
- **CI runs in the same image.** The `e2e` job runs in `mcr.microsoft.com/playwright:v1.61.1-noble`, pinned by digest (`.github/workflows/ci.yml`), so CI's screenshots are comparable with a sandbox run's.
- **The sans in the captures is the image's `system-ui`.** In the Playwright browser image that resolves to WenQuanYi Zen Hei, a single Regular face, and Chromium neither has nor synthesises a bold for it. Labels, legends, alert titles, `h4` and `**bold**` therefore render at regular weight in the screenshots. This is the image's fonts, not our CSS: `font-synthesis` is only turned off for Fraunces, and the same CSS renders real bold with any system sans that has one (Liberation Sans in the same image: 286 → 312 px for one string at 400 → 700).

**Forced colours.** `e2e/stub/forced-colours.spec.ts` emulates `forced-colors: active` and focuses, from the keyboard, the three elements that hide the browser's outline (`focus-visible:outline-hidden`): a card's link, the main content after a client navigation, and an error page's heading. It asserts the outline is still drawn, and takes a checkpoint of each (journey `forced-colours`), in both themes as usual. axe checks each state twice (`inForcedAndAuthorColours` in `e2e/support/journey.ts`). First it runs in forced colours, on the page as it is captured, with every rule but `color-contrast`. axe-core has no forced-colours support: Chromium paints the system palette, but `getComputedStyle` reports the author `color` next to the forced `background-color`, so the contrast rule would pair colours that are never painted together. Then it runs with forced colours turned off, with every rule, contrast included. The screenshots are taken in forced colours. Two more tests, with plain assertions and no checkpoint: a facet checkbox on `/pieces` (focus outline drawn, `appearance: auto` so the system draws the box, and Space ticks it) and a conservation badge on a piece's page (a solid border, one icon, and a focus outline).

**Accessible names that are read out.** A facet checkbox is named exactly "Song, 3 pieces" (`FacetGroup`: one `sr-only` run, no space before the comma), asserted exactly in the unit tests and `browse.spec.ts`; an absolutely positioned (`sr-only`) span counts as a block in the name, so a comma in a separate span would be preceded by a space in a browser, though not in jsdom. Child-route errors are `h2`s (`UnderPageHead`): the history and members error tests assert one h1.

`target: "<selector>"` limits axe and the screenshot to one element, such as a styleguide block. The sticky header and the app bar are hidden during that capture, so they are never painted over it. The element is scrolled to the top of the viewport, which is made taller if the element still doesn't fit (Chromium paints anything beyond the viewport as bare canvas), and the capture has 8 px of room around it so an outset focus ring shows whole. With `target` and `viewportOnly`, axe covers the element and the screenshot is the viewport. Use this for an open dialog with its scrim, or toasts in place. `atEachViewport` rebuilds a width-specific state (the account panel, the drawer) at each width.

### Adding a journey

1. **Put the spec in the right phase.** Use `e2e/prod/<journey>.spec.ts` if the page works in the production build. Use `e2e/stub/` if it needs sign-in or the styleguide. Import `test` from `../support/test` and `expect` from `@playwright/test`.
2. **Make the data you need.** Create a fresh fixture user with `createFixtureUser(request, {...})` and sign in with `page.goto("/auth/login?as=<id>&returnTo=/path")`. Inject failures with `failNext`. Never rely on another test's state.
3. **Wait for hydration** with `waitForHydration(page)` before clicking or typing anything that needs JS.
4. **Declare a checkpoint** for each new page or key state in `e2e/support/checkpoints.ts`, and call `checkpoint(page, "<name>")` in its own test. A checkpoint is slow, so keep other sweeps out of that test.
5. **Sweep new pages.** A new page a reader can land on also gets a row in `JOURNEY_PAGES` (`e2e/support/journey-pages.ts`) with its primary controls.
6. **No-JS behaviour** goes in that phase's `no-js.spec.ts`. Don't use `test.use({ javaScriptEnabled: false })` anywhere else.
7. **Run it filtered**, e.g. `npm run test:e2e -- e2e/stub/<journey>.spec.ts`, then run the full suite once so the teardown checks the screenshot set.
